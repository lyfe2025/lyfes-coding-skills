# 编写有效测试

本参考文档用于补充 TDD 的 RED → GREEN → REFACTOR 主流程。重点是证明用户可观察的行为，而不是证明实现“看起来像对的”。

## 先定义 production break

每个测试都应能回答：如果实现出现哪一种真实回归，这个测试会失败？

- 先写清输入、行为和期望结果。
- 期望值必须独立推导，不要从待测实现复制。
- 测试错误路径、边界值和空值，不只测 happy path。

## 避免无效断言

不要只检查：

- 源码中是否出现某个字符串。
- 私有字段是否存在。
- 常量被原样返回。
- mock 被调用了几次，却没有验证用户可见结果。

这类断言可能在功能失效时仍然通过。优先通过公共 API、文件产物、命令退出码或实际副作用验证行为。

## Mock 的边界

- 默认使用真实代码；只有外部服务、时间、随机数或不可控资源才 mock。
- mock 必须保留测试所依赖的真实副作用和数据结构。
- 如果 setup 很大、mock 很多，优先考虑更小的接口或真实集成测试。
- 不要为了测试在 production class 中增加 test-only 方法或状态。

## 变异检查

完成测试后，临时改变实现中的关键行为，确认测试确实会失败；随后恢复实现并重新运行全套测试。可以通过删除分支、改错边界条件或替换期望值完成，而不必引入 mutation testing 工具。

## Review 清单

- [ ] 测试名称描述行为，而不是实现步骤。
- [ ] 期望值不是从实现复制出来的 mirror assertion。
- [ ] 至少覆盖一个真实失败路径或边界路径。
- [ ] 断言检查结果/副作用，而非只检查调用记录。
- [ ] mock 数量和 setup 保持必要的最小范围。
- [ ] 已进行一次变异检查，确认测试能抓住回归。
